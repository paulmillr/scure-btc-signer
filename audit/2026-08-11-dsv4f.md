# Audit 2026-08-11 (dsv4f): Low-priority follow-ups

Scope: `src/*.ts`.

This file contains the six legitimate low-priority items remaining after severity
reassessment. The SegWit-v0 prevout fee-manipulation issue was addressed separately.
The reported in-place Taproot sorting and ElligatorSwift scalar-validation issues
were omitted because they do not affect the current implementation as alleged.

---

## 1. `combine()` accepts conflicting singleton metadata (Informational/Low)

Location: `src/transaction.ts` — `Transaction.combine`; `src/psbt.ts` —
`mergeKeyMap`.

When two PSBTs for the same unsigned transaction contain different values for a
non-keyed metadata field, `combine()` may retain the value supplied by the latter
PSBT. Relevant fields include `witnessUtxo`, `nonWitnessUtxo`, `redeemScript`, and
`witnessScript`.

This behavior is permitted by BIP174, which allows a combiner to choose either
value when duplicated singleton keys conflict. It is nevertheless surprising and
order-dependent. The merge path reruns script consistency checks, so incompatible
wrapper metadata is normally rejected rather than silently producing a usable
alternative spend.

Potential impact: confusing or invalid combined PSBTs and failed signing/finalizing
workflows. No direct loss of funds is expected.

Possible hardening: reject conflicting understood singleton fields instead of
selecting one, or expose a strict-combine mode.

## 2. `Transaction.sign()` suppresses per-input errors (Informational)

Location: `src/transaction.ts` — `Transaction.sign`.

`sign()` attempts every input, suppresses individual `signIdx()` errors, and
returns the number of inputs it signed. This behavior is useful when one key owns
only some inputs, but it also hides why other matching inputs were skipped. A
caller that ignores the returned count may discover the problem only during
finalization.

Potential impact: delayed error discovery or an unexpectedly partial PSBT. The
transaction cannot be extracted through the normal API until all inputs are
finalized, so this is not a direct loss-of-funds issue.

Possible hardening: add a reporting API that returns signed, skipped, and failed
input indices with their errors. Keep `signIdx()` as the strict per-input API.

## 3. Imported wrapper scripts are not checked before finalization (Low)

Locations: `src/transaction.ts` — `Transaction.fromPSBT`, `signIdx`, and
`finalizeIdx`.

`fromPSBT()` validates the PSBT structure but does not immediately verify that a
`redeemScript` or `witnessScript` matches the hash committed by the previous
output. A normal `signIdx()` call indirectly performs this check when it stores
the generated signature through `updateInput()`, and `combine()` also checks
merged inputs. However, `finalizeIdx()` can consume signatures already present in
an imported PSBT without rerunning the wrapper check.

Potential impact: creation of an invalid final script or witness, causing the
transaction to fail validation and stall the signing workflow. The mismatched
script cannot redirect the signed outpoint or outputs.

Possible hardening: run `checkScript()` at the start of `finalizeIdx()` and make
the signing-boundary check explicit rather than relying on the later update path.

## 4. Imported ECDSA partial signatures may be high-S (Low)

Location: `src/transaction.ts` — `Transaction.finalizeIdx`.

Signatures produced locally by `signECDSA()` are already low-S because the
underlying noble signer uses low-S normalization by default. Imported
`partialSig` entries are embedded during finalization without checking or
normalizing their S value.

A high-S ECDSA signature is consensus-valid for relevant pre-Taproot script paths
but violates standard Bitcoin relay policy.

Potential impact: a finalized transaction may be rejected from mempools and fail
to relay, stalling the spend until the signature or transaction is rebuilt. No
direct theft is enabled.

Possible hardening: validate DER encoding and the appended sighash byte, then
reject or normalize high-S signatures before finalization.

## 5. Taproot fee estimation assumes key-path availability (Low)

Location: `src/utxo.ts` — `estimateInput`.

When `tapInternalKey` is present and is not the unspendable key, the estimator
assumes a key-path witness. The field is metadata and does not prove that the
available signer can produce a key-path signature. A wallet may carry both the
internal key and script leaves while only being able to satisfy a script path,
which can require a larger witness.

Potential impact: underestimated transaction weight and fee, resulting in slow or
failed relay and a need to fee-bump or rebuild the transaction. Principal is not
directly at risk.

Possible hardening: expose an explicit spend-path estimation option. When signer
capability is unknown, conservatively estimate an applicable script path rather
than inferring key-path availability from `tapInternalKey` alone.

## 6. BIP370 locktime selection uses field counts instead of compatibility (Low)

Locations: `src/transaction.ts` — `Transaction.lockTime` and
`Transaction.combine`.

The locktime getter counts inputs containing height- and time-based requirements
and chooses height when the height count is at least the time count. BIP370 instead
requires choosing a locktime type supported by every locktime-constrained input,
then taking the maximum value of that type. Mutually incompatible requirements
must not be treated as a majority vote.

Because `combine()` compares the currently derived unsigned transactions before
merging metadata, separately compatible PSBTs can pass the equality check and
become incompatible after their locktime fields are combined. The resulting
derived locktime can change unexpectedly.

Potential impact: invalid signatures, a non-final transaction, or selection of a
locktime type that does not satisfy the intended spending conditions. No direct
loss of funds is expected.

Possible hardening: implement BIP370's all-input compatibility algorithm, reject
incompatible height/time requirements, and revalidate the derived locktime after
combination.
